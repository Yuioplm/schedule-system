## 2. 全体アーキテクチャ（データの流れ）

1. `scripts/` がDB初期状態を作る
   - テーブル/ビュー作成
   - マスタ投入
   - 日付・祝日作成
2. `streamlit_app/pages/` が業務操作（登録・検索・編集・出力）を担う
3. 帳票ページが `sql/*.sql` を `streamlit_app/sql_loader.py` 経由で実行
4. 運用時は `T_ScheduleChange` / `T_TemporarySchedule` 更新結果が `V_ScheduleActual` に反映される

## 6. 代表シナリオ別 影響調査ルート

### 6.1 「予定変更が帳票②に出ない」

1. `3_予定変更入力.py` で登録済みか確認
2. `5_変更登録履歴.py` で `Rpt2Flag` / `ActiveFlag` を確認
3. `Report2.sql` の抽出条件を確認
4. `7_帳票2.py` 画面の期間条件を確認

### 6.2 「反映後予定に変更が出ない」

1. `T_ScheduleChange` の最新レコードが有効か確認
2. `T_TemporarySchedule` の登録日・有効状態を確認
3. `ActualScheduleSearch_base.sql` / `V_ScheduleActual` のロジック確認

### 6.3 「新しい診療科が選択肢に出ない」

1. `12_マスタ管理.py` で `M_ClinicalDepartment` を確認
2. `ActiveFlag` と表示順設定を確認
3. 対象画面（枠管理・変更入力・帳票）で再確認

## 7. 変更種別ごとのレビュー観点

### 7.1 ページ（UI）変更
- 入力項目がDBカラム定義と一致しているか
- 既存の業務導線（予定検索→変更入力→反映後確認）を壊していないか

### 7.2 SQL変更
- 列名/型の変更がページ側参照に影響しないか
- 帳票出力フォーマット（列順・見出し）に差異がないか

### 7.3 scripts変更
- `set_up.py` 実行フローと矛盾しないか
- 既存運用DBへの再実行安全性が確保されているか
